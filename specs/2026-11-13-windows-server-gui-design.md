# Guardian Server for Windows — design

Date: 2026-11-13. Status: draft, awaiting owner approval. Builder check done (2026-11-13).

## Intent

Today the Guardian server (`server/`, Go + SQLite) runs only on Linux, and the class
is managed from the Android app. The owner wants a classroom to work with **nothing but
the teacher's own Windows computer**: the teacher opens one GUI application at the start
of the lesson, it runs the server, and the teacher blocks applications and computers
**directly in that window**, without a phone and without a separate always-on server.

## Who and when

- The **teacher**, on their own computer in the classroom, at the start of a lesson.
- Students' computers already run the agent (Windows or Linux) and point at the teacher's
  computer.

## Goals

1. A Windows GUI app, **Guardian Server**, that starts the existing server in-process when
   opened and stops it when closed.
2. Manage the class from one screen (layout **B**, chosen by the owner, see below).
3. First run needs no configuration: the app generates `TOKEN` and `ADMIN_TOKEN` itself,
   stores them, and shows them for copying.
4. Agents find the teacher's computer **by its Windows computer name**, because the
   router may give the teacher a different IP from day to day.
5. Ships in the release archive next to the Linux server.

## Non-goals

- No change to the agent. It already keeps enforcing the last state from `sync.json`
  when the server is unreachable, so blocks stay active when the teacher closes the app
  or shuts the computer down (owner's decision; verified in `agent/main.go`, `updateSync`).
- No Windows service / always-on server: the server runs only while the window is open.
- No computer names. Computers are shown by their `IDENTITY` number as "PC 7"; the owner
  explicitly dropped naming.
- No network discovery (agent broadcast). The owner chose the computer-name approach;
  spoofing by a fake server is not a concern for this audience (owner's call).
- No change to the Android app; it keeps working against the same server in parallel.
- No agent on the teacher's computer (owner's decision). The README says so: an agent
  there would show up as a PC and be caught by **Block all PCs**. Nothing in the app
  detects or excludes it.
- No multi-tenant / Postgres work (that lives on `dev`).

## Anti-goals

- The teacher must not need to edit files, open a terminal, or configure the firewall by
  hand to get a lesson going.
- The window must not silently show "running" when the server failed to listen.
- A second copy of the server logic: the GUI must reuse `server/`'s handlers and database
  code, not reimplement the API.

## Decided by the owner

- Runs on the teacher's classroom computer; started by the teacher.
- Blocks persist when the app closes (agent's last state).
- Address in `agent.env` is the computer name, e.g. `SERVER_ADDRESS=http://PROFESOR-PC:8080`.
- Tokens are generated by the app on first run.
- Layout **B — everything on one screen**:
  - **Top bar:** server state (running / stopped, with the reason when it failed, e.g.
    "port 8080 is in use"); protection on/off (the server's `enabled` flag — the phone's
    shield button); class mode blacklist / whitelist; red **Block all PCs** and
    **Unblock all**; **Connect…** button.
  - **Left — Applications:** the server's application list; each row has the enabled
    checkbox and the app's mode; **+** adds a process by name; an app can be removed.
  - **Right — Computers:** every computer that has synced, shown as "PC <IDENTITY>", with
    online / blocked / offline state and a Block / Unblock button; a header like
    "9/12 online".
  - **Connect window:** the exact line for `agent.env`
    (`SERVER_ADDRESS=http://<COMPUTERNAME>:8080`), `TOKEN`, the phone's address and
    `ADMIN_TOKEN` (hidden until "Show"), each with **Copy**. If the computer name does not
    resolve on the network, a warning with the current LAN IP as a fallback.
- Computers are identified by number only.
- The teacher's computer does not run an agent.
- UI language: **English**, like Guardian Console.

## Builder's calls (made by Claude, not agreed by the owner — check these)

- **Technology:** Go + `lxn/walk`, like Guardian Console (`tools/whitelist-gui`), built
  32-bit so one exe runs on 32- and 64-bit Windows. Reuses that tool's build pattern
  (`rsrc` manifest + icon, `-H windowsgui`).
- **Embedding the server:** refactor `server/` so the HTTP server can be constructed and
  run from another Go program (e.g. move the code into an importable package and keep
  `server/main.go` as a thin Linux entry point), with an explicit DB path, listen address
  and tokens instead of reading `./.env` / `./guardian.db` from the working directory.
  The Linux binary's behaviour and API must stay identical.
- **GUI talks to the server in-process** (direct calls into the server's cache/DB layer)
  rather than over HTTP to itself — the builder may choose HTTP-to-localhost instead if it
  keeps the refactor smaller; either way changes made from the phone must show up in the
  window (refresh every ~3 s).
- **Online rule:** a computer is online if its last sync is under 60 s old, the same rule
  as the Android app (`computers_screen.dart`, `_isComputerOnline`).
- **Application ordering:** disabled first, then alphabetical, as in the Android app.
- **Data location:** `%ProgramData%\Guardian Server\` holds `guardian.db` and `.env`
  (`TOKEN`, `ADMIN_TOKEN`, port), so it survives reinstalling the exe.
- **Tokens:** 32 random bytes each from `crypto/rand`, URL-safe base64.
- **Port:** 8080 by default (matches agents and the phone's default); configurable in the
  `.env`, not in the UI.
- **Firewall:** the app asks for administrator rights (manifest `requireAdministrator`,
  like Guardian Console) and, if missing, adds one inbound Windows Firewall rule for its
  TCP port, **all profiles** (school networks are often classified Public) but
  `remoteip=LocalSubnet` (`netsh advfirewall`).
- **Single instance:** a second launch focuses the existing window instead of failing on
  the port.
- **Closing the window** stops the server cleanly (graceful shutdown, DB closed). No tray icon.
- **Reachability instead of a name check:** Windows always resolves its own name, so a
  self-check proves nothing. The top bar shows "last agent sync N s ago". If the server
  has been running for 2 minutes with no agent sync at all, the window shows a warning
  that agents may not find `<COMPUTERNAME>` and gives the current LAN IP as a fallback.
- **Phone address:** the Connect window shows both `http://<COMPUTERNAME>:8080` and
  `http://<current LAN IP>:8080` for the phone, noting the IP may change: Android
  generally cannot resolve Windows computer names. Windows agents use the name (LLMNR /
  NetBIOS via the system resolver); Linux agents usually resolve it through
  systemd-resolved's LLMNR, otherwise they need the IP or a DHCP reservation — README
  documents this.
- **Timestamp bug fix (server):** `computers.datetime` is SQLite `CURRENT_TIMESTAMP`
  (UTC, no offset) while `current_time` is local time with an offset, so on a server not
  set to UTC the phone shows every PC offline. The server returns `datetime` as RFC 3339
  UTC (`...Z`). Same instant on a UTC Linux server; update `specs/api.md`. The window uses
  the same corrected values.
- **Packaging:** `scripts/package.sh` cross-compiles it on Linux into
  `server-windows/GuardianServer.exe` in the release archive, with a short `README.txt`
  (first run, admin prompt, what to copy into `agent.env`, no agent on this computer,
  name-resolution caveats).
- **Location in the repo:** `tools/server-gui/` (its own `go.mod`, like the console).

## Constraints

- `modernc.org/sqlite` is pure Go, so the server cross-compiles to `windows/386` with
  `CGO_ENABLED=0` — the whole release still builds on the Linux CI runner.
- Release CI runs only on push to `main`; any new tests must run there
  (`.github/workflows/release.yml`).
- The project rule: update `specs/server.md`, `specs/api.md` (only if the API changes —
  it should not), `CLAUDE.md`, `README.md` and `CHANGELOG.md` with the change.

## Left to the builder

- Exact widget layout, sizes, colours and wording (in English).
- How the server refactor is split into files.
- Tests: at least the refactored server constructor (temp DB path, tokens), token
  generation, the `.env` read/write, and the online rule; a window smoke test like the
  console's `window_test.go` if it runs in CI.

## Success

A teacher downloads the release, double-clicks `GuardianServer.exe` on their classroom
computer, accepts the admin prompt, copies the `agent.env` line and token into the agents,
and within a minute sees the class's computers in the window and can block an app and a
PC — with the phone app still able to connect to the same server.

## Goal

Переносное приложение для Windows, которое запускается с флешки на машине с агентом Guardian и
ничего не устанавливает. Оно читает конфигурацию агента, его кэш политики и его журнал в
Windows Event Log и показывает в одном окне:

- работает ли защита, а если нет — почему и что делать;
- что агент закрывал и когда;
- что он закроет прямо сейчас, если запустить конкретную программу.

С правами администратора оно также позволяет поправить настройки агента (`.env`) и локальный
список разрешённых программ (`whitelist.txt`) и перезапустить службу, чтобы правка вступила в
силу.

Задача — за пару минут на месте ответить на вопросы «почему не работает» и «почему закрывается
программа X» и исправить локальную причину, без кабинета и без копания в `System32`.

## Background

- **Что агент оставляет на машине** (папка `C:\Windows\System32\ProcSentinel\agent`, путь берётся
  из `ImagePath` службы `ProcSentinelAgent`):

  | Файл / источник | Содержимое | Секрет | Правится приложением |
  |---|---|---|---|
  | `.env` | `SERVER_ADDRESS`, `CHECK_INTERVAL`, `BINDING_TOKEN` (до привязки) | `BINDING_TOKEN` | да |
  | `agent_credentials.json` | `agent_token`, `machine_guid`, `server_address`, `enrolled_at` | `agent_token` | нет |
  | `sync.json` | последняя политика: `mode` (`blacklist`/`whitelist`/`free`) и `applications[]`; mtime = время последней успешной синхронизации | — | нет |
  | `whitelist.txt` | локальный список разрешённых процессов (действует только в режиме `whitelist`) | — | да |
  | Event Log `Application`, источник `ProcSentinelAgent` | всё, что агент пишет в режиме службы: старт, синхронизации, ошибки привязки и сети, **каждое убийство** (`Killed process: X`, `Killed non-whitelisted process: X`) | — | нет |

- **Журнал блокировок на сервере** складывается из записей, которые агент держит в памяти до
  отправки. С диска их не прочитать. Но каждое убийство агент дублирует в Event Log, поэтому
  локальная история убийств доступна в объёме журнала `Application` (по умолчанию 20 МБ,
  старые записи перезаписываются).
- **Логика решения агента** (`enforce` в `agent/agent.go`, `isSystemProcess` в `agent/main.go`):
  - `blacklist`: агент выполняет `taskkill /F /IM <правило>`, если текст правила — подстрока
    вывода `tasklist` (без учёта регистра); закрывается только процесс, чьё имя **равно**
    правилу (без учёта регистра); правило со `*` не срабатывает никогда;
  - `whitelist`: закрывается всё, чего нет ни в `applications`, ни в `whitelist.txt`, ни во
    встроенном защищённом списке;
  - `free`: ничего не закрывается.
- **Как агент читает файлы, которые приложение правит.** От этого зависят правила записи:
  - `.env` (`readEnvFile`, `agent/client.go`): построчно; пустые строки и строки с `#`
    пропускаются; ключ и значение — по первому `=`, с `TrimSpace`; кавычки **не** снимаются; при
    повторе ключа побеждает последняя строка. `SERVER_ADDRESS` агент дополнительно обрезает от
    хвостовых `/`. `CHECK_INTERVAL` — целое > 0, иначе значение по умолчанию.
  - `whitelist.txt` (`loadWhitelist`, `agent/main.go`): построчно, `TrimSpace`, строки с `#`
    пропускаются, сравнение в нижнем регистре.
  - Оба файла читаются **один раз при старте службы**. Правка без перезапуска не действует.
  - Если `whitelist.txt` **нет**, агент при старте генерирует его из всех запущенных процессов
    (`initWhitelist`). Поэтому приложение никогда не удаляет этот файл.
  - Если агент привязан (`agent_credentials.json` есть и его `server_address` совпадает с
    `SERVER_ADDRESS`), `BINDING_TOKEN` в `.env` **игнорируется** (`agent/agent.go`, `loadCredentials`
    → `step`). Если `SERVER_ADDRESS` изменён, агент считает себя непривязанным и для новой
    привязки ему нужен `BINDING_TOKEN`.
- **Ловушка запуска.** В режиме `whitelist` (или на заблокированной машине) агент убивает любой
  незащищённый процесс в течение секунды, включая программу, запущенную с флешки. Без
  исключения приложение не откроется именно там, где нужнее всего.
  - Защищённые имена — только из встроенного списка агента.
  - `guardian.exe` уже в нём (для Guardian Console). Поэтому бинарник называется
    **`Guardian.exe`**.
- **Стек и архитектура — по образцу PdfCraft** (`bucket/pdfcraft`):
  - cargo workspace, ядро без GUI, платформенный слой, оболочка egui;
  - правила «never panic», `unsafe_code = "forbid"`;
  - режим без GUI (отчёт в консоль) поверх того же ядра.
- **Что уже было в Go-консоли** (`tools/whitelist-gui`): health-сигналы, обход WOW64 через
  `Sysnative`, чтение журнала через `wevtutil`, правка `whitelist.txt` с нормализацией имён
  (`normalizeName`), чтение и запись `.env` с сохранением неизвестных ключей (`envfile.go`).
  Логика берётся оттуда (`specs/whitelist-gui.md` → Installation State Detection, WOW64
  Redirection), без функций установки, обновления и удаления.

## Scope

**In scope:**
- один переносной `Guardian.exe` (x86, работает на 32- и 64-битной Windows 10+), запуск с любого
  носителя без установки;
- вкладки Diagnostics, Configuration, Processes, Log; интерфейс на английском;
- правка `SERVER_ADDRESS`, `CHECK_INTERVAL`, ввод и удаление `BINDING_TOKEN` в `.env`;
- правка `whitelist.txt`: добавление вручную, добавление из списка запущенных процессов, удаление;
- резервная копия перед каждой записью, атомарная запись, перезапуск службы `ProcSentinelAgent`
  по подтверждению;
- проверка доступности сервера (`GET /health`);
- сохранение отчёта на флешку рядом с exe;
- команда `Guardian.exe report` (текст/JSON в консоль) для того же отчёта без окна;
- тесты ядра на фикстурах, проверки согласованности с исходниками агента, CI.

**Out of scope:**
- установка, обновление и удаление агента (остаются за Go-консолью до установщика на Rust,
  см. Open questions);
- правка `agent_credentials.json` и `sync.json`; перепривязка удалением credentials;
- старт/стоп службы как отдельные действия (только перезапуск после сохранения);
- правка `.env` и `whitelist.txt` из командной строки (`report` остаётся только для чтения);
- обращения к серверу, кроме анонимного `GET /health`; никакой авторизации;
- серверный журнал блокировок и кабинет;
- macOS/Linux, сборка под ARM64;
- изменения агента и сервера.

## Requirements

**Запуск и безопасность**

1. `Guardian.exe` — один файл, без установщика, без DLL рядом, со статическим CRT. Запускается
   двойным кликом с флешки на 32- и 64-битной Windows 10+ (`i686-pc-windows-msvc`).
2. Приложение пишет на машину **только** `.env` и `whitelist.txt` агента и их резервные копии
   (`*.bak-YYYYMMDD-HHMMSS` в папке агента), только по кнопке Save и только с правами
   администратора. Ничего не пишется в реестр, `%APPDATA%`/`%ProgramData%` и другие файлы
   агента. Вторая запись — файл отчёта по явной кнопке, в папку рядом с exe
   (`GuardianReports\`); команда `report` пишет её же, только когда у exe нет консоли (см. 25).
   Если флешка защищена от записи, кнопка сообщает об этом и предлагает
   выбрать другую папку.
3. Манифест `asInvoker`. Без прав администратора приложение показывает всё, что смогло прочитать.
   Каждое недоступное поле помечено «no access», а не ошибкой. Правка в этом режиме недоступна:
   поля вкладки Configuration только для чтения, сверху плашка «Run as administrator to edit».
   Кнопка «Restart as administrator» перезапускает `Guardian.exe` через `runas` с аргументом
   `--tab <вкладка>`, и новое окно открывается на той же вкладке. Старое окно закрывается, как только
   запущен новый процесс; при отказе в UAC старое окно остаётся.
4. Секреты (`BINDING_TOKEN`, `agent_token`) никогда не показываются, не копируются и не попадают
   в отчёт. Вместо значения — «present / absent» и последние 4 символа SHA-256 (чтобы сравнить два
   файла, не раскрывая токен). Новый `BINDING_TOKEN` вводится в поле-пароль и после сохранения
   в памяти приложения не хранится.
5. Если агент не установлен, приложение показывает это как диагноз («service not found, default
   folder is empty») и не падает. Можно вручную выбрать папку (например, сохранённую копию с
   другой машины). Для такой папки вкладки Configuration и Processes считаются по выбранной
   папке, а служба и журнал — по текущей машине. Это явно подписано. Правка в выбранной вручную
   папке разрешена, но перезапуск службы не предлагается.

**Вкладка Diagnostics** (открывается первой)

6. Сверху — итоговый вердикт одной строкой с цветом состояния:
   - «Protection is on»;
   - «Protection is on with a stale policy (no contact with the server for N h)»;
   - «Not enrolled»;
   - «Service stopped»;
   - «Not installed» (в том числе когда службы нет, а папка агента есть, и когда служба
     запущена, но её exe отсутствует);
   - «Free mode: nothing is closed». Сервер присылает `free` в трёх случаях: машина не в
     комнате, защита комнаты выключена, комната удалена. По `sync.json` их не различить, поэтому
     подсказка называет все три и отправляет в кабинет.
7. Под вердиктом — список проверок. У каждой: статус (ок / внимание / ошибка), факт и строка «что
   делать». Минимальный набор:

   | Проверка | Источник | Внимание / ошибка |
   |---|---|---|
   | Служба зарегистрирована и запущена, тип запуска Auto | SCM | не найдена; остановлена; запуск не Auto |
   | Exe службы существует | `ImagePath` | указывает на отсутствующий файл |
   | Версия агента | `procsentinel-agent*.exe -version` | не удалось определить |
   | `SERVER_ADDRESS` задан | `.env` | пусто |
   | Сервер отвечает | `GET {SERVER_ADDRESS}/health`, таймаут 5 с | нет ответа, DNS, TLS, не 200 — с текстом ошибки |
   | Привязка | `agent_credentials.json` | файла нет; `server_address` в нём ≠ `SERVER_ADDRESS` (агент считает себя непривязанным) |
   | Остаток `BINDING_TOKEN` | `.env` | есть после привязки (агент не смог его стереть или его игнорирует) |
   | Последняя синхронизация | mtime `sync.json` против `3 × CHECK_INTERVAL` | файла нет; устарел (с возрастом) |
   | Несохранённые в службе изменения | mtime `.env` / `whitelist.txt` против времени старта службы (Event Log) | файл изменён после старта службы: «changes apply after the service restarts» |
   | Ошибки агента за 24 ч | Event Log | есть `Error`: последние три сообщения |
   | Отказ сервера | Event Log | сообщения «token is no longer valid», «no longer accepts this computer's token», «plan limit reached» (каждая строка проверяется по исходникам агента/сервера в `agent_consistency.rs`) — с переводом на человеческий |
   | Часы машины | `Date` в ответе `/health` против локального времени | расхождение > 5 мин |

8. Кнопка Refresh перечитывает всё. Автообновления нет: снимок состояния стабилен, пока его
   читают. Если на вкладке Configuration есть несохранённая правка, Refresh спрашивает
   «Discard unsaved changes?».

**Вкладка Configuration**

9. Показывает:
   - настройки агента из `.env` (см. 11); неизвестные ключи — отдельным списком только для
     чтения, с пометкой;
   - привязку: `machine_guid`, сервер, дату `enrolled_at`;
   - политику из `sync.json`: режим, время синхронизации, таблицу приложений (имя, список);
   - `whitelist.txt` (см. 12);
   - встроенный защищённый список (свёрнут).

   Имена процессов, пути, GUID и время — моноширинным шрифтом.
10. Отдельно указано, что `whitelist.txt` действует только в режиме `whitelist`, а оба файла
    читаются агентом один раз при старте службы. Если файл изменён позже последнего старта
    службы (время старта берётся из Event Log), показывается жёлтая плашка «Changes apply after
    the service restarts» с кнопкой «Restart service».
11. **Agent settings** (правка — только с правами администратора, см. 3):
    - `SERVER_ADDRESS`: поле ввода. Допустимо `http://` или `https://`, непустой хост,
      необязательный порт, без пути, query и fragment. Хвостовые `/` обрезаются при сохранении,
      как это делает агент. Пустое значение — ошибка.
    - `CHECK_INTERVAL`: целое от 1 до 86400 (секунды). Пустое значение удаляет ключ из `.env`, и
      агент использует значение по умолчанию; это подписано.
    - `BINDING_TOKEN`: текущее значение не показывается (только «present / absent» + хвост хэша).
      Поле-пароль для нового токена: пустое поле — «не трогать». Кнопка «Remove» помечает токен
      на удаление. Значение проходит те же ограничения, что и любое значение `.env` (см. 13).
    - Предупреждения перед сохранением (в диалоге подтверждения, сохранение не блокируют):
      - `SERVER_ADDRESS` ≠ `server_address` из `agent_credentials.json` и нового токена нет:
        «This computer will drop out of the fleet until it gets a new binding token»;
      - введён новый `BINDING_TOKEN`, а агент привязан к этому же серверу: «The agent ignores a
        binding token while this computer is enrolled. Unenrol it in the cabinet first, then
        save the token again.» Токен всё равно записывается по подтверждению;
      - `CHECK_INTERVAL` < 5: «A short interval adds load on the server».
12. **Local whitelist** (правка — только с правами администратора):
    - таблица записей с фильтром; у записи, уже покрытой встроенным защищённым списком, пометка
      «already protected»;
    - «Add»: поле ввода. Имя нормализуется как в `normalizeName` Go-консоли: `TrimSpace`, нижний
      регистр, снятие кавычек `"` и `'`, от вставленного пути остаётся только имя файла. `.exe`
      **не** добавляется автоматически; имя без `.exe` получает предупреждение «tasklist reports
      names with .exe». Пустое имя, имя с `#` в начале и дубликат отклоняются с объяснением;
    - «Add from running»: список запущенных процессов (из того же снимка, что вкладка
      Processes) с множественным выбором; уже присутствующие и защищённые помечены;
    - «Remove» для выделенных строк;
    - удаление всех записей допустимо: файл остаётся, с одной строкой-комментарием (см. 14).
13. Общие ограничения значений `.env`: значение не содержит перевода строки и `#` в начале, не
    начинается и не заканчивается пробелом (агент сделал бы `TrimSpace`, и записанное не совпало
    бы с прочитанным). Нарушение — ошибка, Save недоступен.
14. **Запись**. Правка — черновик в памяти; сверху счётчик несохранённых изменений, кнопки Save и
    Revert. Save:
    1. Проверка (см. 11–13). Ошибки блокируют Save, предупреждения показываются в диалоге
       подтверждения вместе с кратким диффом («SERVER_ADDRESS: a → b», «+ winword.exe»,
       «− game.exe»; токен — только «set» / «removed»).
    2. Файл перечитывается с диска и сверяется с хэшем из снимка. Если он изменился после
       чтения: диалог «<file> changed on disk since it was loaded» с выбором «Reload» (черновик
       теряется) или «Overwrite».
    3. Перед записью все изменённые файлы сверяются с ожидаемым хэшем (ошибка чтения —
       отдельное сообщение, не «changed on disk»); ни один файл не пишется, пока не проверены
       все. Для каждого файла: копия текущего содержимого (тех же проверенных байтов) в
       `<file>.bak-YYYYMMDD-HHMMSS` (локальное время), затем запись во временный файл в той же
       папке, `sync_all` и замена через `std::fs::rename` (на Windows это `MoveFileExW` с
       `MOVEFILE_REPLACE_EXISTING`; без `unsafe`), затем повторное чтение и сравнение с
       записанным. Из резервных копий одного файла (только имена вида
       `<file>.bak-YYYYMMDD-HHMMSS` с необязательным `-N`) хранятся 5 самых новых, старшие
       удаляются; только что созданная копия не удаляется никогда. В копии `.env` значение
       `BINDING_TOKEN` заменено на `<removed by Guardian>` (R14.3).
    4. Ошибка на любом шаге — сообщение с текстом ошибки и путём к резервной копии; черновик
       сохраняется, чтобы можно было повторить. Если записан один файл из двух, это прямо
       сказано.
    5. После успешной записи — диалог «Restart ProcSentinelAgent now?». «Restart» —
       stop + start через SCM с таймаутом 30 с на каждую фазу, прогресс в окне. Отказ — остаётся
       плашка из 10.
    6. Снимок пересобирается полностью, вкладка Diagnostics отражает новое состояние.
15. **Правила рендера файлов** (минимальный дифф, побайтно сохраняется всё, что не правилось):
    - `.env`: значение меняется только в **последней** строке с этим ключом (её читает агент),
      остальные строки с тем же ключом не трогаются. Отсутствующий ключ дописывается в конец.
      Удаление ключа убирает **все** строки с ним (как `removeEnvKey` агента). Сохраняются
      комментарии, пустые строки, порядок, неизвестные ключи и окончания строк (CRLF или LF —
      по преобладающим в исходном файле; для нового файла CRLF). BOM UTF-8 в начале сохраняется.
    - `whitelist.txt`: существующие строки (включая комментарии и пустые) сохраняются в исходном
      порядке; удалённые записи выкидываются; новые дописываются в конец. Если записей не
      осталось и в файле нет других строк, записывается
      `# Local whitelist is empty. Do not delete this file: the agent regenerates it on start.`
    - Файл в кодировке не UTF-8 (например, UTF-16 с BOM) и файл больше 1 МБ не правятся:
      вкладка показывает «Cannot edit: <причина>», просмотр остаётся.

**Вкладка Processes**

16. Список запущенных процессов (`tasklist /FO CSV /NH`) с вердиктом по текущей политике из
    `sync.json`, вычисленным **так же, как `enforce` агента**:
    - «Protected by the system»;
    - «Allowed (whitelist.txt)»;
    - «Allowed (policy)»;
    - «Will be closed» (в `blacklist` — имя процесса равно правилу без учёта регистра);
    - «Not affected» (режимы `blacklist`/`free` для остальных процессов).

    Вердикт считается по **сохранённым** файлам, а не по черновику Configuration. С правами
    администратора у строки «Will be closed» есть действие «Add to local whitelist», которое
    добавляет имя в черновик и переключает на Configuration.
17. В режиме `blacklist` агент закрывает процесс командой `taskkill /F /IM <правило>`, но только
    если `strings.Contains(tasklistText, rule)`. Поэтому закрывается процесс, чьё имя **равно**
    правилу (без учёта регистра). Если правило лишь входит подстрокой в имя другого процесса
    (`code.exe` и `vscode.exe`), агент каждую секунду пытается убить `code.exe`, пишет
    «Failed to kill process …», а `vscode.exe` не затрагивается: у строки `vscode.exe`
    показывается пометка «substring match: rule `code.exe` (the agent will try, but
    `vscode.exe` is not closed)», вердикт — «Not affected». Правило со `*` никогда не проходит
    проверку `Contains`, не срабатывает вовсе, и это тоже отмечается.
18. Поле «Why is … closed?»: имя программы, в том числе не запущенной, и ответ с правилом и его
    источником.
19. Фильтр по имени и переключатель «only what will be closed».

**Вкладка Log**

20. Записи источника `ProcSentinelAgent` из журнала `Application` (`wevtutil qe … /rd:true /f:xml`,
    последние 2000), новые сверху. Колонки: время (локальное), уровень, сообщение.
21. Фильтры: Kills, Errors and warnings, Sync, All, поиск по тексту, период (1 h / 24 h / 7 days
    / all).
22. Режим «Kill summary»: убийства, сгруппированные по процессу. Для каждого — сколько раз,
    первое и последнее время, причина (`blacklist` для «Killed process», `whitelist` для «Killed
    non-whitelisted process»). Это локальный аналог журнала блокировок кабинета. С правами
    администратора у строки с причиной `whitelist` есть «Add to local whitelist» (как в 16).
23. Внизу — сколько записей прочитано и с какого времени журнал хранит историю. Так видно, что
    старшие записи вытеснены, а не «их не было».

**Отчёт**

24. «Save report» пишет `GuardianReports\<hostname>-<YYYYMMDD-HHMM>.txt` и `.json` рядом с exe.
    Существующий отчёт никогда не перезаписывается: при совпадении имени добавляется суффикс
    `-1`, `-2`, …. Внутри:
    - вердикт и проверки;
    - конфигурация без секретов (по сохранённым файлам, не по черновику);
    - политика;
    - вердикты процессов;
    - последние 500 записей журнала;
    - версии агента и приложения;
    - имя и ОС машины.

    После сохранения показывается путь.
25. `Guardian.exe report [--json] [--dir <папка агента>]` печатает тот же отчёт в консоль, без
    окна. Коды выхода:
    - `0` — защита работает;
    - `10` — есть предупреждения;
    - `11` — есть ошибки;
    - `2` — ошибка использования.

    Код выхода отражает и вердикт: «Protection is on» → `0`; устаревшая политика, режим free,
    неизвестно → не меньше `10`; не установлено / остановлена / нет регистрации / не было
    синхронизации → `11`.

    `report` ничего не пишет на машину, кроме случая, когда у `Guardian.exe` нет консоли или
    stdout: тогда отчёт сохраняется в `GuardianReports\` рядом с exe и показывается окно
    сообщения. `Guardian.exe` — GUI-приложение, cmd не ждёт его завершения: читать код выхода и
    вывод нужно так: `start /wait Guardian.exe report > report.txt`.

**Архитектура и качество**

26. Workspace `tools/guardian-diag/`:

    | Крейт | Роль |
    |---|---|
    | `crates/core` | Разбор `.env`, `agent_credentials.json`, `sync.json`, `whitelist.txt`, CSV `tasklist`, XML `wevtutil`; модель снимка `Snapshot`; проверки и вердикт; симуляция `enforce`; отчёт. Модуль `core::edit`: модель правки, проверка, рендер новых файлов (см. Technical approach). Без ОС и без GUI, тестируется на любой ОС. |
    | `crates/winhost` | Сбор снимка на Windows: SCM (`windows-service`), реестр (`winreg`), файлы с подменой `Sysnative`, `tasklist`/`wevtutil`/`agent -version` через `Command` с `CREATE_NO_WINDOW`, `/health` через `ureq` + `rustls-native-certs` (как в PdfCraft), перезапуск окна через `runas`. Модуль `winhost::apply`: проверка прав, резервные копии и их ротация, атомарная запись, сверка после записи, перезапуск службы. |
    | `crates/ui-egui` | Четыре вкладки поверх `Snapshot`, черновик правки в состоянии UI. Сбор снимка, запись и перезапуск службы идут в фоновом потоке, окно показывает прогресс и не зависает. |
    | `apps/guardian` | `Guardian.exe`: окно (`--tab <name>`) или `report`, иконка и манифест через `winresource`. |

27. `core` получает данные только через `Snapshot`, собранный `winhost`, и отдаёт `winhost` только
    готовый `WritePlan` (пути, новые байты, ожидаемые хэши исходных файлов). В тестах `Snapshot`
    собирается из фикстур (`tests/fixtures/`: настоящие по форме файлы агента и выгрузки
    `wevtutil`/`tasklist`).
28. Правила «never panic»: `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, …)]`,
    `unsafe_code = "forbid"` во всём workspace. Битый или огромный файл (обрезанный JSON,
    `.env` в UTF-16, гигабайтный `whitelist.txt`) даёт предупреждение в проверке, а не падение.
    Размер читаемых файлов ограничен: 1 МБ на файл, 2000 записей журнала.
29. **Согласованность с агентом** проверяется тестами `core`, которые читают исходники агента из
    репозитория:
    - защищённый список совпадает со списком в `isSystemProcess` (`agent/main.go`);
    - строки «Killed process: %s» и «Killed non-whitelisted process: %s» есть в
      `agent/agent.go`;
    - имена файлов и ключи `.env` совпадают с константами агента;
    - **круговой тест правки**: для каждой фикстуры и каждой правки файл, выданный
      `render_env` / `render_whitelist`, разобранный эталонным парсером, повторяющим
      `readEnvFile` / `loadWhitelist` (последний ключ побеждает, `TrimSpace`, `#`), даёт ровно
      значения из правки.

    Если агент меняется, тест падает в CI, а не тихо врёт на месте.
30. Рендер: eframe с `glow`, без wgpu. Это меньше размер для флешки, а OpenGL есть на любой
    машине с драйвером. Если окно не создаётся, показывается системный диалог `rfd` с советом
    запустить `Guardian.exe report > report.txt`.
31. Тёмная тема и шрифты кабинета (Inter, Space Grotesk, JetBrains Mono), цвет только для
    состояния — как в кабинете и мобильном приложении. Несохранённая правка и плашка «changes
    apply after restart» — амбер (состояние «ожидает»). Шрифты берутся из `mobile/assets/fonts/`
    при сборке (`include_bytes!`), без копий в репозитории. Интерфейс на английском, как
    остальной продукт.
32. CI `.github/workflows/diag.yml` срабатывает на изменения в `tools/guardian-diag/**`,
    `agent/**`:
    - на `ubuntu-latest`: `cargo fmt --check`, `clippy -D warnings`, `cargo test` (ядро, правка и
      проверки согласованности);
    - на `windows-latest`: сборка `--release --target i686-pc-windows-msvc`, smoke-тест
      `Guardian.exe report --dir <фикстура>` с проверкой кода выхода и тесты `winhost::apply` на
      временной папке (резервная копия, ротация, замена, сверка; без службы).

    Артефакт сборки — `Guardian.exe`.
33. Документация: `specs/guardian-diag.md` (итоговое описание после реализации), раздел в

## User / system flow

1. Учитель жалуется: «на 5-м компьютере не открывается Word». Администратор вставляет флешку и
   запускает `Guardian.exe`.
2. Агент в режиме `whitelist`, но `guardian.exe` защищён, поэтому окно открывается. Появляется
   индикатор «Reading service, files, log…» (1–3 с).
3. Diagnostics: «Protection is on. Last sync 12 s ago». Все проверки зелёные.
4. Processes → «Why is … closed?» → `winword.exe` → «Will be closed: whitelist mode, not in the
   room policy or whitelist.txt».
5. Log → Kill summary: `winword.exe` ×14, последний раз 1 мин назад.
6. Два пути:
   - **Для всей комнаты.** Администратор добавляет `winword.exe` в правила комнаты с телефона.
     Через ~20 с нажимает Refresh: синхронизация свежая, `winword.exe` — «Allowed (policy)».
   - **Только для этой машины.** «Add to local whitelist» → плашка «Run as administrator to
     edit» → «Restart as administrator» → UAC → окно на Configuration с `winword.exe` в
     черновике (черновик до повышения прав не переносится, поэтому имя добавляется заново) →
     Save → «Restart ProcSentinelAgent now?» → Restart. Processes: `winword.exe` — «Allowed
     (whitelist.txt)».
7. Save report → `E:\GuardianReports\LAB-A-05-20261013-1412.txt`.

**Сценарий «не работает»:** вердикт «Protection is on with a stale policy (no contact with the
server for 3 days)». Проверка «Server responds» показывает ошибку DNS, а «Agent errors» — «Sync
failed: … no such host». В `.env` опечатка в адресе. Configuration (с правами администратора) →
`SERVER_ADDRESS` исправлен → Save. Предупреждение: адрес не совпадает с `server_address` в
credentials, машина выпадет из парка до новой привязки. Если исправленный адрес совпадает с
адресом в credentials, предупреждения нет. Restart → через `CHECK_INTERVAL` проверка
синхронизации зелёная.

## Technical approach

**Модель:**

```rust
pub struct Snapshot {
    pub taken_at: SystemTime,
    pub machine: MachineInfo,                   // hostname, ОС, архитектура
    pub install: Located<InstallDir>,           // путь + откуда взят (служба / по умолчанию / вручную)
    pub elevated: bool,                         // процесс с правами администратора
    pub service: Read<ServiceInfo>,             // Read<T> = Ok(T) | Missing | Denied | Failed(String)
    pub agent_version: Read<String>,
    pub env: Read<SourceFile<EnvFile>>,         // SourceFile = исходные байты + хэш + mtime + разбор
    pub credentials: Read<Credentials>,         // без токена: только хэш-хвост
    pub sync: Read<SyncState>,                  // + mtime
    pub whitelist: Read<SourceFile<Vec<String>>>,
    pub processes: Read<Vec<String>>,
    pub events: Read<Vec<AgentEvent>>,          // время, уровень, сообщение, Kind (Kill{process, reason} | Sync | ServiceStart | Error | …)
    pub health: Read<HealthProbe>,              // статус, задержка, Date сервера, текст ошибки
}

pub fn diagnose(s: &Snapshot) -> Diagnosis;            // вердикт + проверки
pub fn verdict_for(s: &Snapshot, process: &str) -> ProcessVerdict; // симуляция enforce
pub fn report(s: &Snapshot, d: &Diagnosis) -> Report;  // текст и JSON без секретов
```

`Read<T>` — главный тип: вкладки и отчёт честно различают «нет файла», «нет доступа» и «битый
файл». Токены не попадают в разобранные структуры, только их хэш-хвост. Исходные байты `.env`
лежат в `SourceFile` только для рендера правки: они не выводятся в UI и отчёт и не
сериализуются.

**Правка (`core::edit`):**

```rust
pub enum TokenEdit { Keep, Set(String), Remove }

pub struct EnvEdit {
    pub server_address: String,
    pub check_interval: Option<u32>,            // None = удалить ключ
    pub binding_token: TokenEdit,
}

pub struct WhitelistEdit { pub entries: Vec<String> }   // нормализованные, без дублей

pub fn normalize_name(input: &str) -> String;
pub fn validate(s: &Snapshot, env: &EnvEdit, wl: &WhitelistEdit) -> Vec<Issue>; // Issue { severity: Error | Warning, field, message }
pub fn render_env(original: &[u8], edit: &EnvEdit) -> Result<Vec<u8>, RenderError>;
pub fn render_whitelist(original: &[u8], edit: &WhitelistEdit) -> Result<Vec<u8>, RenderError>;
pub fn plan(s: &Snapshot, env: &EnvEdit, wl: &WhitelistEdit) -> Result<WritePlan, Vec<Issue>>;
// WritePlan { files: Vec<FileWrite { path, expected_hash, new_bytes }> } — только изменённые файлы
```

**Запись (`winhost::apply`):**

```rust
pub fn apply(plan: &WritePlan) -> Result<Applied, ApplyError>;   // бэкап → temp → MoveFileExW → сверка, по файлу
pub fn restart_service(progress: impl Fn(Phase)) -> Result<(), ServiceError>;
```

`ApplyError` называет файл, шаг (`Changed`, `Backup`, `Write`, `Replace`, `Verify`) и путь к
резервной копии, если она уже сделана.

**Порядок работ** (каждый шаг — зелёный коммит):
1. Workspace, `core` с разбором всех источников и фикстурами, тесты согласованности с агентом,
   CI на Linux.
2. `diagnose`, `verdict_for`, `report`; команда `report` с `--dir` по фикстуре.
3. `core::edit`: нормализация, проверка, рендер, план; golden-тесты и круговой тест с эталонным
   парсером агента.
4. `winhost`: сбор снимка на Windows; `winhost::apply` и перезапуск службы; тесты `apply` на
   временной папке; ручная проверка на Windows 10 x64 и x86, с правами администратора и без.
5. `ui-egui`: четыре вкладки, тема, сохранение отчёта, режим правки, повышение прав через
   `runas --tab`.
6. Сборка на `windows-latest`, smoke-тест, документация (включая пометку Go-консоли).

## Edge cases & error handling

- **32-битный процесс на 64-битной Windows.** Файлы агента читаются и пишутся через
  `Sysnative`, а наружу (в UI и отчёт) идут только канонические пути `System32`.
- **Нет прав администратора.** Отсутствующие поля показываются как «no access», вердикт
  учитывает это: «could not check», а не «error». Правка недоступна (требование 3).
- **Отказ в UAC.** Старое окно остаётся как было, сообщение «Elevation was cancelled».
- **Файл изменён на диске между чтением и сохранением** (агент стёр `BINDING_TOKEN` после
  привязки, другой администратор, Go-консоль). Требование 14.2: Reload или Overwrite.
- **Агент держит файл открытым или антивирус блокирует замену.** `MoveFileExW` возвращает ошибку
  доступа; повтор 3 раза с паузой 200 мс, затем сообщение с путём к резервной копии. Исходный
  файл не тронут, временный удалён.
- **Перезапуск службы не уложился в 30 с** или служба не стартовала. Сообщение с состоянием
  службы и последними ошибками из Event Log; файлы уже записаны, это сказано прямо. Повторить
  можно кнопкой «Restart service» из плашки (требование 10).
- **В режиме `whitelist` перезапуск службы** даёт окно в несколько секунд без защиты. Это
  указано в диалоге перезапуска одной строкой.
- **Новый `BINDING_TOKEN` при действующей привязке.** Агент его игнорирует; предупреждение из
  требования 11 отправляет в кабинет для unenrol. Приложение credentials не трогает.
- **Агент запущен, но `sync.json` никогда не создавался.** Вердикт «Never synced». В журнале
  видно, привязка это или сеть.
- **`server_address` в credentials не равен `SERVER_ADDRESS`.** Агент считает себя
  непривязанным. Это отдельная ошибка с объяснением, а не просто «not enrolled». На вкладке
  Configuration рядом с полем — кнопка «Use <адрес из credentials>», чтобы вернуть адрес одним
  нажатием.
- **`.env` содержит ключ несколько раз.** Показывается значение из последней строки (как у
  агента) с пометкой «defined N times, the last one is used»; правка меняет только последнюю.
- **`whitelist.txt` отсутствует.** Показывается «absent — the agent generates it from the
  running processes on its next start». Save создаёт файл (без резервной копии, её не из чего
  делать).
- **`.env` отсутствует.** Save создаёт файл с введёнными ключами (CRLF).
- **Журнал `Application` очищен или переполнен.** История убийств короче, чем кажется. Блок
  «log holds entries since …» это показывает.
- **Источник `ProcSentinelAgent` не зарегистрирован** (агент запускали только из консоли). Журнал
  пуст; это объясняется подсказкой, а не ошибкой. Время старта службы неизвестно, поэтому
  проверка «changes apply after restart» показывает «could not check».
- **Сервер за HTTPS с самоподписанным сертификатом.** Проверка показывает ошибку TLS как есть и
  не отключает проверку сертификатов.
- **`SERVER_ADDRESS` указывает на внутренний адрес, а машина в другой сети.** Ошибка сети с
  подсказкой, что агент продолжает работать по последней политике.
- **Блокировка машины.** Сервер присылает `whitelist` с пустым списком
  (`server/handlers_agent.go`): закрывается всё, кроме защищённых процессов и `whitelist.txt`.
  Если режим `whitelist` и `applications` пуст, приложение показывает «looks like this computer
  is locked in the cabinet (or the room allows nothing)»: по файлу эти случаи не различить.
  Добавление в `whitelist.txt` в этом состоянии — легальный способ разрешить программу на одной
  машине; предупреждения нет.
- **Флешка извлечена во время работы.** Окно уже в памяти и продолжает работать. Save report
  сообщает об ошибке записи и предлагает другую папку. Правка файлов агента от флешки не
  зависит.
- **Запуск без агента и без флешки** (например, разработчик на своей машине): режим
  «Not installed» плюс ручной выбор папки — для разбора папки агента, присланной в архиве.

## Open questions

1. **Отношение к установщику на Rust** (спека в `stash@{0}` ветки `rust`). Если он вернётся в
   работу, `core` и `winhost` отсюда станут его основой, а установка — четвёртым модулем
   `winhost`. Решение по нему в эту спеку не входит.

## Decisions

- **Архив установщика не меняется** (2026-10-14, вариант (а)). `server/installer.go` по-прежнему
  кладёт в архив Go-консоль под именем `Guardian.exe`, пока не готов установщик на Rust. Новое
  приложение распространяется отдельно (флешка, страница загрузки). Два разных `Guardian.exe` —
  временная путаница: в `specs/guardian-diag.md` и `README.md` это сказано прямо.
